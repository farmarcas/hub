# Research — Hub de Inovação Farmarcas (MVP)

All technical decisions made by the agent (constitution, principle VIII). There are no open items.

## R1. Stack

- **Decision**:
  - Constitution stack: PostgreSQL 16, API in Node 22 + TypeScript + Express 5 + Zod + Prisma 7, React 18 + Vite + Tailwind 4 frontend, Docker Compose.
  - Reuse the skeletons `backend/node` and `frontend/react` and the root `docker-compose.yml`.
- **Rationale**:
  - It is the project standard and already runs in Compose with healthchecks.
  - It matches the vision's suggestion ("React + TypeScript + Vite; API REST; Postgres").
- **Alternatives considered**: none. Changing the stack would need a justification that does not exist.

## R2. Frontend in TypeScript

- **Decision**:
  - Migrate `frontend/react` from JSX to TSX (TypeScript strict).
  - Add `react-router-dom` (routes), `lucide-react` (icons, as the README asks), `tailwindcss` + `@tailwindcss/vite`, `clsx`, `tailwind-merge`, `@fontsource/rubik` (font) and `vitest` (tests of pure functions).
- **Rationale**:
  - The `component-development` skill requires TS contracts (`{Name}Props`, no `any`).
  - The skeleton is only a "status" screen, so the migration cost is close to zero.
  - `@fontsource/rubik` delivers the same OFL font as the prototype without copying binaries out of the bundle.
- **Alternatives considered**:
  - Keep JS: rejected because it breaks the skill.
  - three.js for the globe: rejected, see R4.
  - A data-fetching library (TanStack Query): rejected because the MVP has few screens and simple hooks with `fetch` are enough.

## R3. Identification without login (simulated Radar)

- **Decision**:
  - In the MVP the API identifies the person through the `x-hub-user` header, which carries the id of one of the seed users.
  - This only works with `AUTH_MODE=mock`, a variable validated in `env.ts`. It is the default in development.
  - Any other value refuses to start until the real integration exists.
  - The frontend has an "Entrar como" selector (6 users) in the avatar at the bottom of the rail. The choice is kept in `localStorage` and sent in every request.
  - No route trusts the client: the middleware loads the user from the database, and `requireAdmin` checks `is_admin`.
- **Rationale**:
  - The vision asks for "autenticação mock" until the Radar integration.
  - Authentication is a known gap in `AGENTS.md`, so we neither invent JWT nor passwords.
  - Server-side security (access filter, admin) stays real, and the shape of identification can be swapped later without touching the services.
- **Alternatives considered**:
  - Fake login with a password: rejected because the vision says "sem tela de login própria" and it would mean improvising auth.
  - Fixed user without switching: rejected because it would make it impossible to test access per person (SC-002).

## R4. 3D globe

- **Decision**:
  - **2D canvas** with its own perspective projection (d = 3.2), recreating the README's `buildGraph()` and `draw()`:
    - Fibonacci spiral for groups on the inner sphere (r = 0.62);
    - solutions on the outer sphere (r = 1) in the direction of the average of their groups, with jitter from the id hash and repulsion;
    - arcs, pulses, inertia, zoom 0.7–1.8, focus with easing and label collision avoidance.
  - Pure math (projection, layout, hash, collision) lives in `src/features/explore/lib/` with unit tests. Drawing lives in a hook that controls the `requestAnimationFrame`.
- **Rationale**:
  - The prototype already does this in 2D canvas.
  - The README asks to "replicar a sensação".
  - Fewer dependencies and less weight.
  - Reduced motion is easy to respect (`motion = 0`).
- **Alternatives considered**: three.js / react-three-fiber. Rejected: heavy and unnecessary for ~20 nodes, and harder to keep labels as text.

## R5. Primary keys and model

- **Decision**: **UUIDv7** generated by the application (`@default(uuid(7))`), the same pattern as the `users` table that already exists.
- **Rationale**:
  - The pattern is already chosen and documented in the schema.
  - IDs travel through the API and should not be sequential (non-admins must not enumerate solutions).
- **Alternatives considered**: bigint. Rejected so as not to mix patterns.

## R6. Soft delete × removals

- **Decision**:
  - `groups` uses `deleted_at` (deleting a group = soft delete).
  - Link tables (`group_members`, `solution_groups`, `solution_related`, `solution_access_groups`, `solution_access_users`) are technical and use physical `DELETE`. They are removed in the same transaction as the group soft delete.
  - Solutions do not get a `deleted_at`, because the product's "delete" is to **archive** (`archived_at`).
  - `categories` without soft delete. The MVP does not delete categories.
- **Rationale**:
  - The README asks that deleting a group "removes the id" from the relations.
  - Keeping the dead link would require filtering `deleted_at` on every join, at a high risk of leaking access.
  - The history of the group itself stays.
- **Alternatives considered**: soft delete on the link tables. Rejected because of the complexity and leak risk in the access filter.

## R7. Symmetric relation between solutions

- **Decision**:
  - Table `solution_related(solution_a_id, solution_b_id)` with `CHECK (solution_a_id < solution_b_id)` and PK on the pair.
  - The service normalizes the order when saving and reads both columns.
- **Rationale**: one row per pair, with no duplicates and no A→B / B→A divergence.

## R8. Access filter

- **Decision**:
  - Single rule in the service `canView(solution, viewer)`, unit tested.
  - In the repository it becomes a Prisma query with an `OR` of three branches (`access_all`, `access_users` contains viewer, `access_groups` ∩ viewer's groups), always together with `status = 'published' AND archived_at IS NULL`.
  - It applies to `/graph`, search, the panel, related items and counts, all derived from the same filtered set.
  - The `/users` screen (admin) uses the same rule to count "Acessa".
- **Rationale**: FR-015 and FR-016, with security on the server.

## R9. Policies

- **Decision**:
  - Fixed content in the frontend (`features/policies/content.ts`), copied from the v5 prototype text, with the "Conteúdo de exemplo" notice.
  - No table and no endpoint.
- **Rationale**: the spec puts editing outside the MVP. Avoiding a table no one edits follows "começar pequeno".

## R10. Categories

- **Decision**:
  - Table `categories(id, name)` with a unique index on `lower(btrim(name))`.
  - `POST /categories` returns the existing one if the name repeats (idempotent).
- **Rationale**: open list and no duplicates (spec edge case). 3NF instead of free text in the solution.

## R11. Status enum

- **Decision**:
  - Postgres enums `group_type ('theme','directorate')` and `solution_status ('in_review','published')`.
  - The API exposes `"Tema" | "Diretoria"` and `"Em avaliação" | "Publicada"`, mapped in the schemas.
- **Rationale**: stable values in the database, Portuguese labels at the edge.

## R12. Seed

- **Decision**:
  - `backend/node/seeds/20261015120000_hub_prototipo.sql` with the 9 groups, 11 solutions, 6 users, memberships, 4 categories, relations and access rules from the v5 prototype.
  - Fixed UUIDs documented, `ON CONFLICT DO NOTHING`, idempotent.
  - Marina Freitas is admin. One more user is admin as well (Tiago Menezes, Dir. Tecnologia), so that removing one admin can be tested.
  - Applied by `npm run db:seed` inside the API container (`psql` via `prisma db execute --file`).
- **Rationale**: SC-005 and the `seed-data` skill (SQL in `seeds/`, UTF-8, fictional data). The prototype answers the skill's business questions, so there is no need to ask.

## R13. Tests

- **Decision**:
  - API: Vitest unit tests for the services, covering the rules:
    - save validation;
    - access filter;
    - group deletion impact;
    - category normalization;
    - symmetry of related items.
  - API: Supertest integration on the test database (happy path, 400, 403, 404, 409).
  - Web: Vitest on the pure functions of the globe and of the access summary.
- **Rationale**: `node-unit-testing` and `node-api-development` skills.

## R14. Desktop first

- **Decision**: layout designed for ≥ 1280 px (desktop and laptop). Below `md` the admin screens stack and the globe stays usable, with no specific mobile polish.
- **Rationale**: the spec puts mobile outside the MVP's priority. The styling skill asks for mobile-first, so the classes are mobile-first, but no mobile design is created.
